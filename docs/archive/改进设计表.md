## 二、已完成项（按批次倒序）

### 批次 P3/P2 收尾（v2.0.0）—— 设计表 16 项清零

这一批把设计表最后 4 项一次做完，项目由 1.x 升到 **2.0**。执行顺序刻意是 **E2 → E1 → C4 → C6**：
E2（构建流程）是 C4（RSS）的前置，先做才不会卡住。

#### E2｜构建流程引入　`✓ 已完成 · v2.0.0`

**原判**：「当前无构建是刻意的简单，避免过早工程化」——这个判断在 1.x 是对的。
**何时反转**：当"没有构建步骤"开始**挡住功能**（C4 的 RSS 必须构建期产出）时，就不再是简单，而是欠债。

**落地（刻意保持最小，不引入打包器）**：

| 文件 | 作用 |
| --- | --- |
| `package.json` | 声明 `gate` / `feed` / `build` / `preversion` / `version:check` 五个脚本 |
| `package-lock.json` | 锁定 jsdom 依赖树（29KB） |
| `tools/check-version.js` | 版本三处一致性自检，不一致非零退出 |

```bash
npm run gate       # 门禁：故障注入 + 功能回归（发布铁律）
npm run feed       # 生成 feed.xml（E2 解锁 C4）
npm run build      # = gate + feed
npm run version:check   # BUILD / LOG / ?v= 三处一致
```

**为什么不上 webpack/Vite**：本项目的本质价值就是"打开就是能跑的静态站"。引入打包器会换来
构建产物、source map、一堆 devDependencies，却换不到任何用户可见的收益 —— **那是把简单换成复杂，不是把简单换成可靠**。
`preversion` 钩子在 bump 前自动跑门禁，这一条才是构建流程真正值钱的地方。

#### E1｜前端错误上报落库　`✓ 已完成 · v2.0.0`

**原问题**：生产白屏时用户不会开 F12，错误永远消失在别人的浏览器里。

**落地**：

- `window.onerror` + `unhandledrejection` 双钩子，`boot()` 里**最先安装**（之后启动阶段崩溃也能被捕获）。
- 脱敏后写云表 `error_logs`：**URL → `[url]`、邮箱 → `[email]`、`wbpk_`/`eyJ` 开头令牌 → `[token]`**，再裁到 1000 字符。
- **原始 error 对象只进 console，绝不入库**（安全基线：对外脱敏）。
- 会话内上报上限 **10 条**，防一个死循环错误把库刷爆。
- **只接 JS 运行时异常，拒收资源加载错误**（img/css 404 也会冒泡到 window 的 `error`）——
  否则几张图挂掉就能吃光 10 条配额，真正的异常反而报不上来。
- 上报通道**自身失败静默** —— 上报不能成为新的错误源。

**表设计要点**：`error_logs` 只对 `anon/authenticated` 开 `INSERT` 与（限自己的）`SELECT`，
**没有 UPDATE / DELETE** —— 日志只能追加，连作者自己都改不了，避免"改日志"这条攻击路径。
`owner_id` 有 `DEFAULT auth.uid()::uuid`（客户端不传归属，由库层按会话身份填充；
须显式转型，`auth.uid()` 返回 text）。

#### C4｜RSS 订阅　`✓ 已完成 · v2.0.0`（E2 解锁）

**当初挂起的原因**：纯静态站无法产出 `feed.xml`；前端 JS 生成的 XML 爬虫抓不到（不执行 JS，与 OG 同一堵墙）。

**E2 之后的解法**：`npm run feed`（`tools/gen-feed.js`）在发布前用 Node 直连云库拉 `status=published`
的文章，落成**静态 `feed.xml`** —— 阅读器直接 GET 就能拿到全文索引。

| 要点 | 处理 |
| --- | --- |
| URL 前缀 | 全部带 `/cyberpunk-blog/`（根路径只是跳转页，写错就是空壳） |
| 发现声明 | `index.html` 加 `<link rel="alternate" type="application/rss+xml">` |
| XML 合法性 | 净化 XML 1.0 非法控制字符，否则整个文件不可解析 |
| 内容 | RSS 2.0 + atom:self 自引用；标题/链接/guid/时间/描述/分类 |

**踩坑**：第一版把 `atom:link` 写成了根域 `/feed.xml`，实际文件在 `/cyberpunk-blog/feed.xml` 下 ——
这类"路径少一层"的错误在浏览器里完全看不出来，只有阅读器订阅失败才会暴露。已修。

#### C6｜亮色主题切换　`✓ 已完成 · v2.0.0`

**原判**：「CSS 变量化改造工作量大，赛博暗色本身是特色，收益存疑」。
**实际**：项目 1.x 就已经全面 CSS 变量化（`:root` 21 个变量），改造量远低于预期 —— **当初的顾虑是错的，属于没看代码先估工**。

**落地**：三态循环 `AUTO → LIGHT → DARK`，存 `localStorage`；导航栏一个按钮切换。

| 设计点 | 处理 |
| --- | --- |
| 霓虹色可读性 | 浅底上青/品红/黄全部**压暗一档**（`#00f0ff → #007a91`），否则亮底亮字根本读不清 |
| 发光效果 | `--glow-*` 在浅底是糊的，收敛为极淡描边 |
| 代码块 | 保持深色（代码在浅底上用浅色反而更难读），但改用变量而非硬编码 |
| 首绘闪烁 | CSP 禁内联脚本 → 无法在首绘前定主题。故**跟随系统走纯 CSS media query（零闪烁）**，手动选择才可能有一帧 |
| 选择器陷阱 | 不用 `:root:not([data-theme="dark"])` 这类写法 —— 它在"系统暗色 + 未手动设置"时同样命中，会误伤 |

#### C2｜文章 TOC 目录 + 代码块复制按钮　`✓ 已完成 · v1.8.0`

**原问题**：长文详情页没有目录，读者只能一路滚；代码块只能手动框选复制。

**落地实现**：

| 部件 | 做法 | 落点 |
| --- | --- | --- |
| TOC 容器 | `postView` 里加 `<nav id="post-toc" hidden>` 占位 | `js/views.js` |
| 目录生成 | `buildToc()` 从 `#md-target` 抽 `h2/h3`，无 id 的自动补 `toc-<slug>-<i>` 锚点 | `js/app.js` |
| 滚动高亮 | `IntersectionObserver`（`rootMargin: '-78px 0px -70% 0px'`）；**不可用时降级**为滚动位置计算 | `js/app.js` |
| 点击定位 | 目录项点击 → `scrollTo` 平滑滚动并补偿 78px 顶部栏 | `js/app.js` |
| 复制按钮 | `bindCodeCopy()` 遍历 `.md-body pre`，`addEventListener` 挂 `<button type="button" class="code-copy">` | `js/app.js` |
| 复制降级 | `navigator.clipboard.writeText` → 失败或不存在时走 `document.execCommand('copy')` 隐藏 textarea 通道 | `js/app.js` |
| 样式 | `.toc` / `.toc-link.active` / `.code-copy`（与 `pre::before` 的 `▸ EXEC //` 角标错位共存，`pre.has-copy` 撑高避让） | `css/style.css` |

**两处细节设计**：
- **标题不足 2 个时目录隐藏**（`nav.hidden = true`）——避免短文留一个空框。
- **`bindCodeCopy` 幂等**（`if (pre.querySelector('.code-copy')) return`）——详情页 `innerHTML` 会重渲染两次，防止按钮叠加。

**约束遵守**：全程 `addEventListener`，零内联事件属性——CSP `script-src` 不含 `'unsafe-inline'`，这是硬前提（回归 R36b/R36c 守着）。

#### C1｜文章搜索　`✓ 已完成 · v1.8.0`

**原问题**：文章多起来后只能靠标签频段翻，没有关键词入口。

**落地实现**：

- 新增 `#/search` 与 `#/search/<关键词>` 两条路由（`parseHash` + `route` + `renderNav` 入口）。
- `renderSearch()` 取数复用 `Posts.listPublished`（`pageSize: 200`），**纯内存过滤** `title / summary / tags`——不含正文（列表接口本就没取正文，硬做就得上库层全文检索）。
- 输入框支持按钮提交与 Enter 提交；空查询显示「索引已就绪 · N 条待扫描」；无命中给 `NO MATCH` 空状态。
- **草稿天然不进索引**——`listPublished` 只返回 `status=published`，与首页同一条 RLS 通道。

**取舍说明**（与设计表原文一致）：设计表约定「先做前端过滤；文章超 50 篇再考虑库层全文检索」。本批严格遵守，未新增任何库层检索 API。

#### C3｜归档页（按月）　`✓ 已完成 · v1.8.0`

**原问题**：没有按时间浏览的入口，只能无限下拉。

**落地实现**：

- 新增 `#/archive` 路由；`renderArchive()` 同样复用 `listPublished`（与 C1 同源，正如设计表所料「做了搜索顺手做」）。
- `groupByMonth()` 按 `created_at` 归组为 `{ key, label, posts }`，**月份倒序 + 组内按接口原始顺序**。
- 每组渲染 `<section class="archive-group">` + 月份标题 + 条数徽标 + `<a href="#/post/:id">` 条目列表（含 `MM.DD`）。

### 批次 P1-2：安全纵深（v1.7.0）

#### A3｜post_images 视图收口 + MIME 白名单　`✓ 已完成 · v1.7.0`

**原问题**（审计 M-2）：`post_images` 的读取策略是 `USING true` —— 匿名访客可 `SELECT` 全部图片行，含 `owner_id` / `storage_path`；写入侧无 `content_type` 类型约束。

**落地实现**（三层收口）：

| 层 | 措施 | 效果 |
| --- | --- | --- |
| 读取通道 | 建视图 `public_images`，只暴露 `id / content_type / data / thumb / width / height / size_bytes / created_at` | `owner_id`、`storage_path` 不再对外可见 |
| 基表策略 | `REVOKE SELECT ON post_images FROM anon`；删除 `post_images_read_all`；新建 `post_images_read_own`（`USING owner_id = auth.uid()`） | 匿名查基表 → **42501 拒绝**；登录用户仅能读自己的行 |
| 写入约束 | `CHECK (content_type IN ('image/jpeg','image/png','image/gif','image/webp'))` | 库层强制 MIME 白名单 |
| 前端纵深 | `toDataUrl()` 经 `safeMime()` 过滤后再拼 data URL；封面选择器同样校验 | 不信任库内返回值，双重保险 |

**实测证据**（改造前后对比）：

```
匿名查 post_images?select=id,owner_id  改造前 → HTTP 200（泄露）
                                       改造后 → HTTP 401 DATABASE_42501 permission denied
匿名查 public_images?select=id,...     改造后 → HTTP 200，返回数据且无 owner_id
匿名查 public_images?select=owner_id   改造后 → HTTP 400 DATABASE_42703 column does not exist
```

**接口兼容性**：对外接口签名完全不变（`NEON.Images.fetchMany / insert` 等保持原形），仅内部读取目标由基表改为视图。写入仍走基表（`owner_id` 由 `DEFAULT auth.uid()` 填充）。

#### A2｜CSP（meta 版先行）　`✓ 已完成 · v1.7.0`

**原问题**（审计 M-1）：全站零安全响应头，XSS 仅靠 `DOMPurify` 单点防线。一旦供应链或某处漏清洗，没有第二道闸门。

**落地实现**：`index.html` `<head>` 加入 meta 版 CSP（网关无法自定义响应头，meta 是唯一可行通道）：

```
default-src 'self';
script-src  'self' https://cdn.jsdelivr.net;
style-src   'self' 'unsafe-inline';
img-src     'self' data: blob:;
connect-src 'self';
font-src    'self' data:;
object-src  'none';
base-uri    'self';
form-action 'self'
```

**逐条依据**（改前端资源时必须同步复核）：

| 指令 | 为什么这么写 |
| --- | --- |
| `script-src` 无 `'unsafe-inline'` | 本站已零内联脚本、零内联事件属性，可用严格策略 |
| `style-src` 含 `'unsafe-inline'` | 大量动态内联样式（编辑器/预览/懒加载回填 `backgroundImage`） |
| `img-src` 含 `data:` | `cloudimg://` 解析出的 base64 图 |
| `img-src` 含 `blob:` | 上传前的本地预览（`URL.createObjectURL`） |
| `connect-src 'self'` | 云数据库/认证/存储均同源 `/.cloud/` |
| `object-src 'none'` | 禁用 `<object>`/`<embed>`，无业务需要 |

**已知局限**：meta 版不支持 `frame-ancestors` 与 `report-uri`，故**防点击劫持与违规上报仍缺失**——需网关支持响应头才能补齐，已在风险台账中留档。

**验证方式**：回归测试断言策略覆盖页面引用的**全部外域**（漏一个就会拦掉自己的资源），并断言「零内联脚本 + 零内联事件属性」——这是 `script-src` 不含 `'unsafe-inline'` 的前提。

#### D2｜版本号 bump 脚本　`✓ 已完成 · v1.7.0`

**原问题**：每次发版要手动改三处（`version.js` 的 `BUILD` + `LOG` unshift + `index.html` 全部 `?v=`），第 2 批实施时已经差点忘。

**落地实现**：新增 `tools/bump.js`，一条命令原子完成三处联动：

```bash
node tools/bump.js 1.7.0 \
  --title="日志标题" \
  --item="条目1" --item="条目2"

# 常用选项
--dry-run     # 只预览不写盘
--no-log      # 只改 BUILD 与 ?v=，不加日志条目
--yes / -y    # 跳过交互确认
--date=...    # 指定日志日期
--build-id=..  # 指定 BUILD_ID（默认自动生成）
```

**能力清单**：

| 能力 | 说明 |
| --- | --- |
| 三处联动 | `BUILD` + `LOG` 头部 unshift + 全部 `?v=` 一次改完 |
| diff 预览 | 写盘前逐行展示变化（位移过大自动收敛为摘要） |
| 版本递增校验 | 新版本 ≤ 当前 BUILD 直接拒绝（防误回退导致缓存键不变） |
| 格式校验 | 非 `x.y.z` 形式拒绝；`--date` 非 `YYYY-MM-DD` 拒绝 |
| 一致性自检 | bump 前若发现 `?v=` 引用不一致，提示并统一 |
| 安全默认 | 非交互环境且未传 `--yes` 时不写盘（防 CI 误触） |

**自证**：本版本（v1.7.0）的 bump 就是用它自己跑的——工具首个用户是它自己的发布流程。

### 批次 P1-1：体验与护栏（v1.6.0）

#### A4｜数据库字段长度上限　`✓ 已完成 · v1.6.0`

- **原问题**：`posts.title / summary / content / tags`、`post_images.data` 均无 CHECK 约束，安全边界只靠前端 maxlength。
- **落地**：6 条 CHECK 约束 —— `posts_title_len≤200` / `posts_summary_len≤500` / `posts_content_len≤200000` / `posts_tags_len≤10`；`post_images_data_len≤3600000` / `post_images_thumb_len≤400000`。
- **实测**：201 字符标题被库层拒绝（`23514`），200 字符放行。
- **⚠️ 落地偏差（重要教训）**：原方案给 `data` 定 `<= 2000000`，但现网唯一一行真实图片（1280×720 PNG）base64 长 **2,058,404** 字符——阈值卡在合法数据之下，约束一加就被数据本身拒绝（`23514 ... is violated by some row`）。不是数据脏，是**阈值拍错**。最终调整为 3,600,000。
  **→ 库层约束阈值必须按真实数据最坏情况留余量，不能凭"够用了"拍脑袋。**

#### C7｜草稿自动保存　`✓ 已完成 · v1.6.0`

- **原问题**：编辑器只在点「保存」时写库；断网、误关标签页 = 长文直接蒸发。
- **落地**：快照分槽 `neon_draft_new` / `neon_draft_p<id>`；`input` 防抖 **3000ms** + `hashchange` 强制落盘；进编辑页检测未恢复快照弹窗询问；保存/发布/删除三条路径清快照；超 4MB 安全线按比例截断并置 `truncated:true`；损坏快照返回 `null` 不抛错。
- **约束遵守**：**不落库**（避免垃圾草稿行），与库内内容逐字段一致时静默清除不打扰。
- **验证**：源码契约断言 + **沙箱实测 8 项**（用 `new Function` 从真实源码抠出 C7 区块真跑一遍）。

#### C5｜OG 分享卡片　`✓ 已完成 · v1.6.0`

- **原问题**：无任何 og: meta，分享到微信/QQ 是裸链接。
- **落地**：站点级 og 全套（`type/site_name/title/description/url/image` + `image:width/height/alt/locale`）+ twitter card；分享图 `assets/og-cover.jpg` 1200×630、121KB。
- **范围说明**：纯静态 SPA 无法为每篇文章动态生成 og（爬虫不执行 JS），故只做站点级——这是设计时明确的取舍，非遗漏。

## 五、文章增删改查（CRUD）边界规则

> 本章是 2.0 收尾时补的。此前规则散落在代码各处，只靠"写的时候想起来"维持；
> 现在集中成一张表，前端校验、库层约束、错误提示三者对齐，改任何一处都要回来同步这张表。

### 5.1 字段定义与约束

字段定义取自线上 `posts` 表真实结构（`information_schema` 实查，非推测）：

| 字段 | 类型 | 可空 | 默认值 | 库层约束 | 前端约束 | 说明 |
| --- | --- | --- | --- | --- | --- | --- |
| `id` | bigint | NO | 自增 PK | — | 只读 | 前端永不提交 |
| `owner_id` | text | NO | `auth.uid()` | RLS | **前端不传** | 由数据库 DEFAULT 填充，客户端传了也会被 RLS 校验 |
| `owner_name` | text | YES | — | — | 取会话昵称/邮箱前缀 | ⚠️ 仍可伪造，见 5.5 |
| `title` | text | NO | — | `char_length ≤ 200` | 必填 + `maxlength=120` | **唯一必填项** |
| `summary` | text | YES | — | `≤ 500` | `maxlength=200` | 空串转 `null`，不存空字符串 |
| `content` | text | NO | `''` | `≤ 200000` | **≤ 200000（`CONTENT_MAX`）** | 允许空正文（先建标题后写），但超限必须拦在前端 |
| `tags` | text[] | NO | `'{}'` | `array_length ≤ 10` | **≤ 8** + 去重 + 单标签 ≤24 | 前端比库层更严，留 2 个余量 |
| `cover_ref` | text | YES | — | — | 须匹配 `cloudimg://数字` | 空串转 `null` |
| `status` | text | NO | `'draft'` | — | 仅 `draft` / `published` | 新建默认草稿 |
| `created_at` | timestamptz | NO | `now()` | — | 只读 | 服务端填充 |
| `updated_at` | timestamptz | NO | `now()` | — | 更新时前端显式传 | 列表按此倒序 |

**为什么要"前端比库层更严"**：库层是最后一道门，改一次要动数据库；前端是体验层，收得紧一点既能提前给提示，也给未来放宽留余地。反之（前端松、库层紧）用户会撞上冰冷的 `23514` 而不是一句人话。

### 5.2 必填校验

| 场景 | 规则 | 失败表现 |
| --- | --- | --- |
| 标题（C/U） | `.trim()` 后非空 | toast「标题不能为空」，**中止提交**，不禁用按钮 |
| 正文（U） | 允许为空 | 不拦截 —— 草稿可以先只有标题 |
| 正文长度（C/U） | `≤ CONTENT_MAX`（200000，与库层 CHECK 对齐） | toast「正文超出上限（N / 200000 字符），请拆分后再保存」，中止 |
| 摘要 | 允许为空 | 空串归一为 `null`（避免列表渲染出空 div） |
| 封面 | 允许为空 | 空串归一为 `null` |
| 封面格式 | 非空时须匹配 `cloudimg://<数字>` | toast「封面引用格式应为 cloudimg://ID」，中止 |
| 会话 | 写操作须已登录 | 库层 RLS 拒绝 → 前端转「权限不足：请先登录再写作」 |

**校验时机**：点「保存草稿」/「发布」时统一 `collectFields()` 收集并校验，返回 `null` 即中止。**不做实时校验** —— 边打字边报红对写作者是干扰。

### 5.3 重复与空值处理

| 情况 | 处理方式 | 理由 |
| --- | --- | --- |
| 标签重复（`代码,代码`） | **去重，保留首次出现的顺序** | 顺序跳变会让用户以为输错了 |
| 标签大小写重复（`JS,js`） | 按小写归一去重，**保留原始大小写** | 既去重又不篡改用户写法 |
| 标签含空项（`a,,b`） | 丢弃空项，不存空串 | 空串标签会渲染成孤零零的 `#` |
| 标签超 8 个 | 截断取前 8 个 | 库层允许 10，前端留 2 个余量 |
| 单个标签超 24 字符 | 截断到 24 | 防止单个标签撑破卡片布局 |
| 分隔符 | 支持中英文逗号与分号 `, ， ; ；` | 中文输入法下容易打出全角 |
| 摘要/封面空串 | → `null` | `''` 与 `null` 语义不同：前者是"有但为空" |
| 正文 | 保持 `''`，不转 null | 库层 `NOT NULL DEFAULT ''`，转 null 会报 23502 |

> 去重实现见 `js/app.js` 的 `normalizeTags()`，集中一处便于测试直接抠出来跑（R50 系列断言覆盖）。

### 5.4 删除确认与越权处理

| 操作 | 确认方式 | 越权/异常表现 |
| --- | --- | --- |
| 删除文章 | **模态框二次确认**（`openModal` + 「确认删除」按钮） | 库层 RLS 限制 `owner_id = auth.uid()` |
| 删除未命中 | 返回 0 行 → 抛「没有删除任何内容：文章不存在或不是你的」 | 静默成功比报错更危险 |
| 更新未命中 | 同上 → 「没有更新任何内容」 | 同上 |
| 发布 / 转草稿 | 不二次确认（可逆，转回草稿即可） | 同上 |
| 离开编辑器（有内容） | `beforeunload` 浏览器原生确认 | 配合 C7 草稿快照兜底 |

**为什么删除要确认、发布不要**：删除**不可逆**，发布**可逆**（一键转回草稿）。确认框的成本应该与操作的可逆性成反比 —— 全都加确认等于全都没确认。

### 5.5 已知未闭环项

| 项 | 现状 | 为什么还没做 |
| --- | --- | --- |
| `owner_name` 可伪造 | 前端提交，客户端可控 | 根治需数据库触发器从 JWT 填充；当前单作者博客，伪造动机极低。**风险已接受并留档**（安全审计 L-2） |
| 标题重复检测 | 不做 | 同名文章是合理场景（如系列文章）；强行拦截比放行更烦人 |
| 软删除（回收站） | 不做 | 真删 + 二次确认对个人博客足够；上软删除要加 `deleted_at`、改所有查询、加清理任务，成本远超收益 |

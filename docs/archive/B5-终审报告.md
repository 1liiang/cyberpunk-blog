## 一、性能审计

### 1.1 分层成本模型（静态分析）

九层氛围的渲染成本分三档（按浏览器渲染管线归类）：

| 层 | 实现 | 成本档 | 说明 |
|---|---|---|---|
| noise / scanline / grid | 静态平铺背景（无动画） | **≈0** | 只在合成时参与，滚不滚都一样 |
| glow / bloom | 静态径向渐变（bloom 带 `mix-blend-mode: screen`） | **低** | blend 有合成开销，但无逐帧重算 |
| signs | `text-shadow` + 7s 周期闪烁 | **低** | 闪烁频率 0.43Hz，远低于 WCAG 3Hz |
| stardust | `background-position` 漂移 + 呼吸 | **中** | 每帧重绘该层纹理 |
| pulse | 扫动的线性渐变（`top` 动画） | **中** | 单元素，合成器可部分优化 |
| **rain** | **DOM 列（每列一个 translateY 合成器动画）** | **最高** | 无 Canvas；列数是成本主因，降档序里排第一 |

> **v4.4.1 变更（见 §六）**：rain 在原稿写作时是"全屏 Canvas 60fps 重绘"；
> 收尾批次把它换成了 DOM 列法 —— 全站**零 Canvas**。分层模型的三档归类不变
> （rain 仍是最贵的一层），但成本结构从"每帧全屏重绘"变为"每列一个合成层"。

### 1.2 保底机制（运行时实测器，已上线）

- **帧率探针**：`atmo.js` 持续采样（3s 窗口），**< 45fps 连续 4 个样本** → 自动降档；
- **降档序**：`rain → stardust → signs → pulse → bloom → glow → grid → scanline → noise`
  （从"最耗且最可牺牲"到"几乎免费"，静态纹理放最后）；
- **用户锁定**：`neon_atmo_lock`（装置面板的"性能锁定"开关）；
- **旁路**：`prefers-reduced-motion` 下动画层**不启动**（JS 与 CSS 双保险）。

### 1.3 实测（已采到 —— 当日补跑）

⚠ 首次尝试因浏览器自动化通道故障（连续 `os error 10060`）未采到；
**当日晚间通道恢复后补跑成功**（探针拆分版：四档 × 静置 3s + 滚动压力 3s + `performance.memory`）：

| 档位 | 层数 | 静置 fps | 滚动 fps | JS 堆 |
|---|---|---|---|---|
| **光污染全开** | 9 | 165.1 | **159.4** | 5 MB |
| 全开**去雨** | 8 | 165.1 | 164.6 | 4 MB |
| 标准档 | 6 | 165.0 | 165.0 | 4 MB |
| 静音档 | 0 | 164.7 | 165.0 | 4 MB |

（测量环境：headless Chrome，无 vsync 限制 ⇒ 绝对值不可直接对照 60Hz 真机；
**档位间的相对差异**是有效信号。）

**读法**：
- **唯一可测出的开销就是数字雨**：全开滚动 159.4 vs 去雨 164.6 —— 差 **3.2%**，
  与分层模型"雨 = 唯一 Canvas"完全吻合（模型被实测印证）；
- 其余八层（含星尘/脉冲两个"中成本"档）在合成压力下**测不出差异**；
- 内存增量 ~1MB 量级；
- 复原核查：审计结束 `data-atmo` 回到 9 层（审计不留痕）。

**结论**：九层光污染的成本可控，"45fps 探针 + 九级降档"是**兜底**而非日常负担 ——
真机（vsync 60fps）下余量充足。

**补跑通道笔记**：`agent-browser eval` 对**长任务（>30s）会超时**（报 10060，与"网络故障"同码）；
把长测量**拆成多次短 eval**（结果暂存 `window.__PERF`）即可 —— 已沉淀进操作笔记。

## 六、v4.4.1 收尾：数字雨换实现风格（§1 的性能结论被改写）

B5 原稿的 §1.3 结论是「数字雨 = 唯一可测开销，滚动 3.2%」。收尾批次按用户要求
**换掉数字雨的实现风格并收紧拖尾参数**，实测结论随之更新 —— 此处如实记录。

### 6.1 为什么换（旧法三个毛病）

旧实现 = Canvas + `destination-out` 半透明擦除：拖尾是「擦不干净」的**副产品**。
后果正好是用户反馈的三点：**过长**（长度随帧率漂移，实测常见 10+ 字符）、
**过密**（列距 26px）、**残留严重**（残余逐帧累积，长拖影糊在屏上）。
三个参数都**不可控** —— 只能靠调擦除透明度"隔靴搔痒"。

### 6.2 新法（DOM 列）

每列一个 `<i class="rain-col">`，整列用 `translateY` 合成器动画下落；
拖尾字符由 JS **精确**生成 4~7 个（不再"擦"，直接"画"）。
离屏即随元素消失 —— **物理上不可能残留**。
参数：

| 旋钮 | 值 | 说明 |
|---|---|---|
| `TAIL_MIN/MAX` | **4 / 7** | 拖尾长度（字符数）——旧法不可控，现精确 |
| `COL_W` | **58** | 列距 px（26→34→46→58，三轮去密；视口约 22 列） |
| `DUR_MIN/MAX` | 7 / 13 s | 单列落屏时长，负延迟错峰 |
| `CHURN_MS` | 180 | 字符流变间隔（每 tick 只换 5 列头字符） |
| 亮度梯度 | 头 78%/0.85 单点小光晕（blur 5px）、次 66%/0.52、三尾 0.55/0.35，底 0.32 | 头亮尾暗、整体压柔 |

### 6.3 性能实测：COL_W 拐点扫描

滚动帧率（同环境对照，基线「全开去雨」= 162.6）：

| COL_W | 列数 | 滚动 fps | 相对基线 |
|---|---|---|---|
| 46 | 28 | 148.5 | **−8.7%（不可接受）** |
| 56 | 23 | 160.8 | −1.1% |
| **58（采用）** | **22** | **164~165** | **≈0%** |
| 64 | 20 | 164.1 | +0.9%（零损耗） |
| 80 | 16 | 164.6 | +1.2% |

**结论：拐点在 56~64，取 58。** 三轮 A/B 复测（全开/去雨交替）22 列稳态损耗 ≈ 0%
（首轮冷启动 9.1% 属预热噪声，二三轮 −0.2% / −0.4%）。

### 6.4 一个被实测否掉的优化（负结果入档）

尝试把 `will-change: transform` 从**逐列**提升到**父层** `.atmo-layer`（+`contain: strict`），
预期"只多一个合成层"。实测**反而恶化到 −9.8%**：父层 `contain: strict` 后，
列的 `translateY` 不再能共享父层合成上下文，合成器仍要为每列单独分配。
**已回退**，并在 `css/style.css` 的 `.rain-col` 注明教训。
→ 定论：**逐列 will-change 是最优；`COL_W`（列数）才是唯一有效的主旋钮。**

### 6.5 其他降本

- 旧法每帧给全列重绘字符 → 新法 `setInterval 180ms` 每 tick 只换 **5 列**头字符；
- 页面隐藏时 `setRainPaused` 挂 `.is-paused`（`animation-play-state: paused`）——
  后台 tab 合成器**零消耗**；
- `text-shadow` 只给**头字符一个**（旧稿"头 1+2 都带 7px 光晕"实测拖低约 8%）。
